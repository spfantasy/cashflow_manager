# 边界情况

ebay_item是订单表引入的，which means如果我们只导入了另外两个表，后者第一个表缺失了一些订单数据，那后两个表数据应该也要支持正常导入，只是页面查询的时候匹配不到title等数据
特殊的，如果涉及退款，那我需要知道退款的order对应哪些item,这时候如果查不到就导入失败即可
ebay_item的主键是item_id; ebay_item_cashflow的主键是cashflow_id，他们都是不重复的，并且存在时应该跳过写入这一行


# 费用分摊规则
首先，整体来说，如果分摊参与者=1，就不用算了都是他的
如果是N个，那就算前N-1个，四舍五入到0.01，最后一个人算残值

W - 均摊规则
按人头来等分，比如现在有N个【参与会员费均摊】的seller
reminder = '15.39 / 3' # 比如3个人分15.39

X - 按lot分配
我们先算出来每个item的应收运费，和实收运费算一个比值，然后将实收分配到item上
例如 item_id = '168058590540' 运费收入15.5（实收）
基础运费的值通过追踪号码来判断
- 如果是ES开头28位的就是9.99
- 如果是XX123456789XX XX代表字母，1-9代表数字一共13位的，例如VR800704956YP，YE180059844CN，UK539678009YP 也是普通物流，9.99刀的基础运费
- 剩余情况是35.99的基础运费

168060971697

168060971728
168061253637
168061253650
除了第一笔(表格顺序上)的其他所有item都有额外运费，计算逻辑通过lot映射
0 < lot <= 5 -> 1美元
5 < lot <= 10 -> 2
10 < lot -> 3

这个例子lot都是1，所以后8个的合并附加运费运费都是1
所以第一笔的reminder= '(9.99 / 9) * 0.862'
其他8个reminder= '(9.99 / 9 + 1) * 0.862'
通过应收9.99+8=17.99 实收 15.5 算出的系数 15.5 / 17.99 =0.862
如果实际数据里面168061253650的lot=6, 那它的合并附加运费就是2，这个情况下：
第1笔的reminder= '(9.99 / 9) * 0.816'
第2-7个reminder= '(9.99 / 9 + 1) * 0.816'
第8个reminder= '(9.99 / 9 + 2) * 0.816'
系数 15.5 / 18.99 =0.816

Y - 按收入分配
先去查order下面所有item的收入和，作为总权重，在算当前item的收入，作为系数，按item的收入在order中的比重分配税费
例如 item_id = '168058590540'
就是(1+X)/(13.41+15.50) * 0.4
reminder = '(1+1.23)/(13.41+15.50) * 0.4' # 比如税费 = 0.4 摊下来的运费收入是1.23

## 补充 1 · 「报告 - 下载 - 所有订单」的真实结构

对应原文「# 外部数据 / 报告 - 下载 - 所有订单 - 1月」与「e.g. 物品编号=168063599278这一行」。

**原文说「每一行可以理解为一个物品(item)」，实测多物品订单不是这样**：多物品订单会先有一行
「订单级汇总行」，其后才是每个物品一行。以订单 `27-14089-26755` 为例：

```
[订单级汇总行] 物品编号=<空>  数量=9  成交价=US $13.41  运费与处理费=US $15.50  付款日期=Jan-17-26  追踪号码=<空>
[物品行]      168058590540  数量=1  成交价=US $1.00   运费与处理费=<空>        付款日期=<空>       追踪号码=ES10031058475954X0101242300N
[物品行]      168058590552  数量=1  成交价=US $1.00   运费与处理费=<空>        付款日期=<空>       追踪号码=ES10031058475954X0101242300N
...
```

因此：

- **订单实收运费（X 的分配基数）与付款日期只写在订单级汇总行上**，物品行上是空的，
  必须从汇总行继承；单物品订单则一行同时带订单级与物品级数据（实测 34 个单物品订单都是这样）。
- 订单级行的 `成交价` = 各物品行 `成交价` 之和（实测 0 处不一致），可以互相校验。
- 文件尾部还有统计行，不能当成数据：`62,笔已下载记录`、`卖家用户名 : lcy-228`。
- 实测有 **2 个订单的订单编号为空**（销售记录编号分别为 18138、18127），
  需要按「销售记录编号」才能把它们拆成两个订单，否则会被并成同一单导致 X 分摊错误。
- 实测有 **4 个物品没有追踪号码**、其订单级运费为 `US $0.00`、且没有付款日期，
  只能退回「出售日期」作为现金流日期（基础运费按规则落到 35.99，但实收 0 所以 X = 0）。
- 实测 57 个追踪号码**全部是 ES 开头 28 位**，没有出现 `XX123456789XX` 形式；
  规则中的 13 位形式按原文保留实现。
- 实测 311 个物品的 `item_id` 无重复；「销售记录编号 ↔ 订单编号」为 1:1（空订单号的两单除外）。
- 原文示例里写的 `track_id`、`buyer_country`、`record_id` 等字段名与实测列一一对得上：
  `销售记录编号 / 订单编号 / 买家用户名 / 买家所在国家/地区 / 物品标题 / 追踪号码 / 成交价 / 运费与处理费 / 付款日期`。

**日期来源（实测确认）**：原文示例的 `cashflow_date = 20260117 #付款日期` 正确；
付款日期缺失时（4 个特殊物品）依次回退到「出售日期」。

## 补充 2 · 「付款 - 交易报告」的真实结构

对应原文「付款 - 交易报告 - 1月」下的四个小节。

实测 1135 行，`类型` 分布：`其他费用 773`、`订单 333`、`发放款项 22`、`退款 5`、`收费 2`。

### 2.1 类型=订单

- 333 行里有 **307 行是物品行**，另有 **26 行「物品编号 = `--`」的订单级汇总行**
  （`净额` = 该订单净额，`物品小计/运费与处理费/成交费 — 固定` 都是 `--`）。
  这些汇总行必须跳过，否则会被当成一个不存在的物品参与分摊。
  校验：原文示例订单的汇总行 `净额 = 24.35`，与 item 级各笔现金流之和完全相等。
- **`成交费 — 固定` 每个订单只写在其中一个物品行上**（实测 60 个订单各写一行 `-0.4`），
  其余物品行是 `--`，所以必须先按订单汇总再按 Y 分摊（原文正是这么要求的）。
- `成交费 — 因品类而异`、`跨国交易费用` 是**逐行读取**的（各物品金额不同，
  如示例订单里为 -0.29/-0.36/-0.45/-1.25），原文的 `成交费 -0.29`、`跨国交易费 -0.02` 与此一致。
- 订单行的 `运费与处理费` 是 **eBay 自己按价格占比**分摊出来的（示例物品为 1.15），
  与原文「X 按 lot 分配」算出的 0.96 并不相同 → 实现时 X 一律用原文算法重算，
  交易报告自带的这一列只在一级兜底场景（订单表未导入）下使用。
- 原文「eBay 收取的税费 是收买家的，但最后 ebay 会全都取走，所以我们不用记现金流」已确认：
  `eBay 收取的税费` 列不生成现金流。退款行的该列为负数（-0.09）。

### 2.2 类型=其他费用（刊登费）

- 772 行是 `描述 = Insertion Fee`（642 行为负、130 行为正即返还），**另有 1 行是 Store 订阅费**
  （`描述 = Store (Basic): Subscription Fee Dec 2025 - Jan 2026`，`净额 = -21.95`，
  `物品编号 = --`，交易创建日期 1-Jan-26）。
- **这行 Store 订阅费与「税费账单」里 `費用組別=訂用服務及一次性費用` 的那一行是同一笔费用**，
  两个文件都记就会重复记账 → 按确认结论：`其他费用` 只处理 `Insertion Fee`，
  会员费统一从税费账单导入。
- 原文示例「168066871033 有两条记录、日期为 20260109 / 20260116」已核对：
  实测该物品两条 Insertion Fee 的**交易创建日期为 8-Jan / 15-Jan，发款日期为 9-Jan / 16-Jan**，
  即**刊登费的 cashflow_date 取「发款日期」**（与原文示例一致）。
- 正负号即区分两条现金流：负数 → `EBAY-TAX-PUB-{item_id}`，正数（返还）→ `EBAY-TAX-PUBRETURN-{item_id}`，
  两者 `cashflow_type` 都是「刊登费」（原文示例的 -0.25 / +0.25 与此一致）。
- 实测刊登费行都有物品编号；`描述` 末尾带空格（`'Insertion Fee '`），比较时需去空白。

### 2.3 类型=发放款项（发款费）

- 22 行，`描述` 统一为「预定发款。已扣除发款费 $X，$Y 已发放，折合 …」，
  可用正则从那句话里取出发款费（原文示例的 -5.91 对应「已扣除发款费 $5.91」）。
- **`发款日期` 这列在发放款项行上是 `--`**，所以日期取**交易创建日期**
  （原文 `EBAY-TRANSACTIONFEE-20260117-李楚吟` 的 20260117 即交易创建日期，已核对）。
- `参考编号` 字段本身就是 `银行参考编号 MZBIL0TEWF5T66I` 这样的完整字符串（原文示例一致）。
- 22 笔发款费合计 30.27，与「税费账单」中 `費用組別=銀行提現費` 的 22 行**按發款編號一一对应**
  （如 7259040393 ↔ $0.39）→ 为避免重复记账，税费账单里的銀行提現費整类忽略，
  发款费统一从交易报告导入。

### 2.4 类型=退款

- 5 行，**`物品编号` 全部是 `--`**，必须按 `订单编号` 反查该订单下的物品。
- `净额` 约 -6.9（原文示例的 -21.95 是另一个月份），`参考编号` 形如 `退款编号 5180906651`，
  日期取「发款日期」（原文示例的 20260116 与实测一致：创建 15-Jan、发款 16-Jan）。
- 其中 1 笔退款的订单 `09-13935-07067` **不在本月订单表里**（12 月的订单），
  按原文边界情况「如果涉及退款…查不到就导入失败即可」处理。
- 退款行的 `成交费 — 因品类而异`（如 +1.00）、`跨国交易费用`（+0.08）、
  `eBay 收取的税费`（-0.09）为**费用返还**，原文只要求记一笔 `净额`，故不单独生成现金流。

### 2.5 类型=收费

2 行信用卡相关扣费（如「累计销售成本的扣款 来自尾号为 0653 的Visa」），按原文忽略。

## 补充 3 · 「付款 - 税费账单」的真实结构

对应原文「付款 - 税费账单 - 1月 / 費用組別=訂用服務及一次性費用」。

- 账单前 6 行是说明信息（賬單日期 / eBay 賣家帳號 / 報告名稱 / 交易平台實體 / 付款實體 / 期間），
  第 7 行才是表头，需要自动定位；列名为繁体：`日期/說明/備註/訂單編號/物品編號/費用組別/費用類型/貨幣/淨額/稅項（%）/稅項金額/總金額/收款實體`。
- 实测 1339 行数据，`費用組別` 共 **5 类**：`刊登費 642`、`成交費 367`、`跨國交易費 307`、
  `銀行提現費 22`、`訂用服務及一次性費用 1`。
- 前四类的处理口径（**原文只提到取「訂用服務及一次性費用」，这里补充为什么**）：
  - `刊登費` / `成交費` / `跨國交易費` 与交易报告重复；
  - `銀行提現費` 与交易报告的「发放款项」按發款編號逐条重复；
  - 因此按确认结论：**税费账单只导 `訂用服務及一次性費用`**，其余整类忽略。
- 该行实测为：`2026-01-01 08:29:00 PDT`、`備註 = 01 月 01 日 - 01 月 31 日`、
  `費用類型 = 商店（一般）：訂用費`、`淨額 = 21.95`（**账单里是正数**）。
  按原文记为 `-21.95`，日期 20260101，reminder 为备注 + 分摊算式（见补充 5）。

## 补充 4 · 三条分摊规则的最终口径

对应原文「# 费用分摊规则」。

原文只对 W 明确写了「如果是 N 个，那就算前 N-1 个，四舍五入到 0.01，最后一个人算残值」。
实现时 **X 与 Y 也采用同一约定**，否则分摊结果之和会与原始总额不相等：

- **X**：原文示例 9 个 lot=1 的物品，每笔按 `(9.99/9 + 1) * 0.862` 算得 1.82，
  加起来是 15.52，而实收运费是 15.50 → 差 0.02 必须由最后一笔吸收（实测最后一笔为 1.80）。
- **Y**：同理，最后一笔取残值，保证订单下各物品的 `成交费 — 固定` 之和严格等于订单总额 -0.40。

其它补充口径：

- **基础运费**取「订单的追踪号码」（同一订单内物品共用同一个追踪号码，实测如此）；
  追踪号码缺失时按原文「剩余情况」记 35.99。
- **「第一笔」的定义**：原文写「除了第一笔(表格顺序上)」，实现为**该订单在报表中出现的第一个物品行**
  （订单级汇总行不算）。原文「168061253650 的 lot=6」的第二个例子中，
  原文写「第8个」而按 9 个物品、应收 18.99 推算应为「第8个（0 起算第 7 个）」，
  两者在应收合计 18.99 上是自洽的，实现按物品的 lot 逐笔取值，不受该笔位置表述影响。
- **Y 的权重**：`物品小计 + 该物品摊到的 X`；分母 = 订单下所有物品的 `物品小计` 之和 + `X` 之和
  （原文示例 `(1+1.23)/(13.41+15.50) * 0.4` 即此结构），
  权重全部为 0 时退化为等分，保证费用不丢。
- **reminder 文案格式**（与原文示例逐字对齐）：
  - X：`(9.99 / 9) * 0.862`、`(9.99 / 9 + 1) * 0.862`（系数保留 3 位小数，附加运费去掉多余小数位）；
  - Y：`(1+0.96)/(13.41+15.50) * 0.4`（订单级费用取绝对值展示，与原文 `* 0.4` 一致）；
  - W：`银行参考编号 MZBIL0TEWF5T66I  5.91 / 3`、`01 月 01 日 - 01 月 31 日  21.95 / 3`
    （即「原文要求的参考信息」+「原文规则要求的 `总额 / 人数`」合并，两者都不丢）。

## 补充 6 · 原文未覆盖、需要拍板后确定的口径

1. **退款分摊算法**（原文写「后续我会给出算法」）：按 Y 的权重（物品小计 + X）分摊；
   但**仅当该订单下所有物品同属一个卖家、且同一个买家时**才执行，
   否则整笔跳过、不入库，并在导入结束后弹对话框提示人工到「手工账」补录。
2. **一件退款分到多个 item 时的 `cashflow_id`**：原文示例 `EBAY-REFUND-5180906651` 是单物品场景，
   多物品时追加 `-{item_id}` 以保证主键唯一（单物品时仍与原文完全一致）。
3. **`--` 一律视为空值**；`物品编号 = --` 的行是订单级汇总行，不参与分摊。
4. **空订单号存 NULL**，这样详情页按订单号筛选时能回退到物品自身的订单号。
5. **同一天多笔发款 / 多笔会员费**会撞「日期-用户」主键：此时不静默丢弃，
   而是报冲突、弹框提示人工处理，避免漏账。
6. **金额精度**：原文要求 `BigDecimal，不要float`。SQLite 没有 DECIMAL 类型
   （NUMERIC 亲和性会把 `'15.50'` 转成 REAL 而丢精度），实现为
   **精确十进制字符串入库 + Python `decimal.Decimal` 运算**，全程不经过 float；
   导出 xlsx 时受 Excel 本身限制写为 2 位小数数字。
7. **样例文件实际是 CSV 而非 Excel**（`报告…csv` / `Transaction…csv` / `invoiceId…csv`），
   实现同时支持 `.csv`（自动尝试 utf-8-sig / utf-8 / gb18030 / big5 / cp1252）与 `.xlsx`。
8. **配置好卖家正则后如何生效**：由于两张表都是「主键已存在则跳过」，
   重新导入不会更新已入库物品的 `seller_name`，因此「页面6 配置」额外提供
   「按当前配置重新匹配全部物品」按钮；「页面4 刊登调整」手工改过的物品会被标记并跳过，不会被覆盖。
9. **`ebay_item` 的扩展列**：除原文点名的字段外，另存 X 所需的派生列
   （`item_price / order_shipping / base_shipping / allocated_shipping / shipping_reminder / payment_date / order_seq`），
   供交易报告导入时计算 Y 使用。
10. **跨月订单兜底**：实测交易报告里有 **512 个 item 的订单数据不在本月订单表内**，
    Y 分摊改为两级：订单明细在 `ebay_item` 里就用原文算法，缺失则退回使用交易报告自身
    同一订单的行（`物品小计` + 该行 `运费与处理费`）作为权重。
11. **`类型=其他费用` 里的 Store 订阅费**跳过（原因见补充 2.2）。
